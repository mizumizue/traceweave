## Content

### Decision
`docs/` 配下のファイル数が増大した場合でも、毎回全ファイルを正規表現や Markdown パーサーでパースする負荷を回避するため、ファイルの mtime（最終更新日時）または content hash をキーとした SQLite キャッシュテーブルを `.cache/traceweave.sqlite` に構築する。

### Structure
- テーブル `doc_cache`:
  - `path TEXT PRIMARY KEY`
  - `mtime_ms INTEGER`
  - `hash TEXT`
  - `meta_json TEXT`
  - `headings_json TEXT`
  - `updated_at TEXT`
- `better-sqlite3` を使用し、WAL モードで同期処理（同期実行により非同期 Promise のオーバーヘッドを排除し、シンプルな手続き型コードで動作）。

### Data Flow
1. パーサーが `docs/` 配下のファイル一覧を取得し、mtime を検査。
2. キャッシュに同一 mtime のレコードが存在する場合は、キャッシュから `meta_json` を即座にデシリアライズ。
3. 変更または新規ファイルのみ `gray-matter` でパースし、キャッシュを更新。
4. 削除されたファイルはキャッシュから削除。

### Trade-offs
- メリット: 数百ファイル規模でもミリ秒単位でパースが完了し、CLI や開発サーバーの応答性が劇的に向上する。
- デメリット: `better-sqlite3` のネイティブバインディングを必要とするが、主要OS向けにプレビルドバイナリが提供されており、手元検証でも問題なくインストール可能であることを確認済み。
