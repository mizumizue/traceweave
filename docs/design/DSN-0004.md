## Content

### Decision
ドキュメントの Markdown 本文全体を単一のプレーンテキストとして扱うのではなく、パーサー側で正規表現 `^###\s+([^\r\n]+)` に基づいて各セクションに分解し、DocNode の `sections` フィールドに格納してフロントエンドに渡す設計とする。さらに ADR-0006 に基づき、テストケース文書（TC）からは動的な実行結果・作文エビデンスを完全排除し、純粋な仕様情報（Objective, Preconditions, Steps, Expected Results）のみをパースする。テスト実行結果（合否ステータス、実測値、ログ証跡）は、テストランナーが出力する機械的レポートから読み出し、データ統合処理において TC ノードに動的マージする設計とする。

### Structure
1. `DocParser`:
   - `## Content` 以下の文字列を `### 見出し名` で分割し、見出し名をキーとするオブジェクトにマップ。
   - テストケース文書の静的パース時は `execution_status` を既定で `pending` とし、静的仕様セクションのみを保持。
2. `TestReportLoader`（または `buildTraceWeaveReport` 連携）:
   - 機械的テスト実行レポートが存在する場合に読み込み、TC-ID をキーとして合否ステータス、実測出力、生ログ証跡、実行時間を TC ノードに動的注入。
3. `DocNode` 拡張:
   - `sections?: Record<string, string>`
   - `execution_status?: 'passed' | 'failed' | 'pending' | 'skipped'`
   - `actual_result?: string`
   - `evidence_log?: string`
   - `execution_duration_ms?: number`
4. `NodeDetailModal.tsx` コンポーネント:
   - ノード種別（NEED, REQ, SPEC, TC）に応じた専用レイアウト。
   - TC 専用ビュー: 静的な「何をテストするのか (Objective, Preconditions, Steps)」と「期待値 (Expected Results)」、およびスクリプト実行による動的な「実測結果 (Actual Results)」と「生ログ証跡 (Evidence)」の対比表示ブロック。未実行時は pending 表示。

### Data Flow
1. Markdown ファイル読み出し → DocParser がフロントマターと仕様セクション本文をパース。
2. テスト結果レポートが存在する場合、TC-ID に基づき動的テスト実行結果（合否・実測値・生ログ）をノードへマージ。
3. SQLite キャッシュおよび静的データペイロード（data.json）にシリアライズ保存。
4. `MatrixBuilder` または CLI/Serve の API が JSON ペイロードに含めて配信。
5. React ダッシュボードでユーザーがクリックした際、ストアから該当ノードを展開して `NodeDetailModal` を表示。

### Trade-offs
- メリット: Git 管理される TC 仕様文書が実行結果や LLM の作文で汚染されず、テストスクリプトの生ログが客観的エビデンスとして直接提示される。
- デメリット: テスト未実行時はエビデンスが表示されないが、これは仕様と実態の乖離を防ぐための意図通りの振る舞いである。
