## Content

### Decision
ドキュメントの Markdown 本文全体を単一のプレーンテキストとして扱うのではなく、パーサー側で正規表現 `^###\s+([^\r\n]+)` に基づいて各セクションに分解し、DocNode の `sections` フィールドに格納してフロントエンドに渡す設計とする。これによりフロントエンドは重い Markdown パーサーライブラリを追加することなく、必要なセクション（Objective, Steps, Expected Results, Actual Results 等）をカードやアコーディオンとして軽量・高速に描画できる。

### Structure
1. `DocParser.parseSections(body: string)`:
   - `## Content` 以下の文字列を `### 見出し名` で分割し、見出し名をキーとするオブジェクトにマップ。
2. `DocNode` 拡張:
   - `sections?: Record<string, string>`
   - `execution_status?: 'passed' | 'failed' | 'pending' | 'skipped'`
   - `actual_result?: string`
3. `DetailModal.tsx` コンポーネント:
   - ノード種別（NEED, REQ, SPEC, TC）に応じた専用レイアウト。
   - TC 専用ビュー: 「何をテストするのか (Objective & Steps)」「期待値 (Expected Results)」「実測値 (Actual Results)」の対比表示ブロック。

### Data Flow
1. Markdown ファイル読み出し → DocParser がフロントマターとセクション本文をパース。
2. SQLite キャッシュにセクション辞書および実測情報をシリアライズ保存。
3. `MatrixBuilder` または CLI/Serve の API が JSON ペイロードに含めて配信。
4. React ダッシュボードでユーザーがクリックした際、ストアから該当ノードを展開して `DetailModal` を表示。

### Trade-offs
- メリット: フロントエンドで Markdown を全構文解析するバンドル肥大化を防ぎ、軽量かつ構造的な対比ビューを高速描画できる。
- デメリット: `### 見出し` の記法に依存するため、見出しレベルが狂った場合はパースが崩れるが、これは CI の `validate-docs.ts` で静的に強制されているため安全。
