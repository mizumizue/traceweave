## Content

### Decision
`.traceweave/config.json` をワークスペース正本とし、解決・読込・マージ・suite 実行を `src/infrastructure/workspace/` と `src/application/run-workspace-tests.ts` に集約する。`resolveProjectLayout`・`TestReportLoader`・`resolve-docs-dir` はワークスペース解決を優先する。TAP パースは `src/core/testing/parseTapTestReport.ts` に抽出し、Node 内蔵ランナー suite と `scripts/run-test-suite.ts` で共有する。

### Structure
- `src/infrastructure/workspace/resolveWorkspaceRoot.ts` — 上方向探索、`TRACEWEAVE_WORKSPACE`
- `src/infrastructure/workspace/loadWorkspaceConfig.ts` — 既定値と suite 解決
- `src/core/workspace/merge-test-results.ts` — 集約マージ
- `src/application/run-workspace-tests.ts` — `traceweave test` / npm test オーケストレーション
- `src/cli/index.ts` — `test` コマンド、グローバル `--workspace`

### Data Flow
1. CLI または `run-test-suite.ts` が `resolveWorkspace()` で `ResolvedWorkspace` を得る。
2. 各 suite を `cwd` で実行。`node-test-tap` は fragment へ、`fragment`/`aggregate` は shell `run` の後に JSON を読む。
3. `mergeTestResultsReports` が集約パスへ書き込む。
4. `buildTraceWeaveReport` が集約のみを `TestReportLoader` で結合する。

### Trade-offs
- メリット: マルチエンジン（Vitest・Python 等）は suite 追加と `fragment` 出力のみ。UI は製品単位の集約を維持。TC 判別は capture アダプタ（現行は TAP タイトル抽出と JSON キー）に閉じる。
- デメリット: 組み込みアダプタは `node-test-tap` に限定。Vitest / JUnit / 無フレームワークはプロジェクト側が traceweave-v1 を書くか、変換スクリプトを `run` に載せる。将来 `src/application/capture/` にエンジン別パーサを追加する想定。
- 拡張方針: 新エンジンは REQ を増やさず SPEC-0028 の `suite.capture` 列挙と実装を追加する。パーサ出力は traceweave-v1 に統一し、マージ以降は `merge-test-results.ts` を共有する。
