## Content

### Decision
MCP サーバーは `src/mcp/` にモジュール分割して配置し、`@modelcontextprotocol/sdk` の `Server` + `StdioServerTransport`（既定）または `StreamableHTTPServerTransport` + `createMcpExpressApp`（`--transport http`）で JSON-RPC を処理する。ドメイン計算は `src/application/` および `src/core/` を直接呼び出し、MCP 層にビジネスロジックを持たない。

### Structure
- `src/mcp/create-server.ts`: `createTraceWeaveMcpServer` — ツール・リソース・プロンプト登録
- `src/mcp/tool-handlers.ts`: 7 ツールの一覧と実行（CLI `matrix` / `catalog` / `decisions` 相当を含む）
- `src/mcp/resource-handlers.ts`: `traceweave-doc://` リソース列挙・読取
- `src/mcp/prompt-handlers.ts`: 3 プロンプトの一覧・取得
- `src/mcp/http-transport.ts`: Streamable HTTP サーバー（stateless、リクエスト毎にサーバー生成）
- `src/mcp/server.ts`: stdio / http 起動エントリ
- `src/cli/index.ts`: `mcp` サブコマンド — docs 解決・トランスポート選択
- `src/application/adopt-project/templates.ts`: `generateMcpConfig` — adopt 時 `.cursor/mcp.json` 生成
- 依存: `buildTraceWeaveReport`, `checkDocs`, `filterCatalog`（既存 Application サービス）

### Data Flow
1. CLI `mcp` が `resolveDocsDir` で文書ルートを決定。
2. `createTraceWeaveMcpServer` が capabilities（tools / resources / prompts）を登録。
3. stdio または HTTP `POST /mcp` で接続を待受。
4. `CallTool` / `ReadResource` / `GetPrompt` 受信時、各ハンドラが Application を呼び出し、結果を JSON または Markdown テキストで返却。
5. adopt overlay が `.cursor/mcp.json` を未存在時のみ生成（`traceweave mcp -d ./docs` 登録例）。

### Trade-offs
- メリット: コアと同一ロジックを共有し、CLI/Web/MCP の結果不整合を防ぐ。リソースで生 Markdown を直接参照でき、プロンプトで反復作業を標準化できる。
- デメリット: HTTP は stateless リクエスト毎にサーバー生成のため高負荷時はオーバーヘッドあり。adopt 生成の `mcp.json` はグローバル `traceweave` CLI 前提で、未インストール時は手動調整が必要。
