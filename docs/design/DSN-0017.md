## Content

### Decision
要件区分をタグや命名規則から推測せず、フロントマターの専用フィールド `requirement_class` として保持する。共有のラベル／判定モジュールを core に置き、パーサー・カタログ・マトリクス・グラフ・CLI・文書検証が同一の許容値と表示ラベルを参照する。検証スクリプトは要件に対して必須チェックを行い、解析器は欠落時もクラッシュせず未設定のまま後段へ渡す。

### Structure
```text
src/core/models/
  types.ts                      # RequirementClass, DocNode.requirement_class, 集計型
  requirementClass.ts           # 許容値判定、FR/NFR ラベル、件数集計、カタログ分割
src/infrastructure/parser/
  DocParser.ts                  # フロントマターから requirement_class を写す
src/core/decisions/
  DecisionsCatalogBuilder.ts    # 項目へ伝播、requirementClassCounts、filter オプション
src/core/matrix/
  MatrixBuilder.ts              # MatrixRow.requirementClass と summary 件数
src/core/graph/
  TraceabilityGraphBuilder.ts   # TraceGraphVisualNode.requirement_class
scripts/validate-docs.ts        # 要件の必須・許容値検査（プロセス検証）
```

### Data Flow
1. Markdown フロントマターの `requirement_class` を `DocParser` が `DocNode` へコピーする。不正値も文字列として保持し、検証側がエラー化する。
2. `DecisionsCatalogBuilder.build` が各項目へ区分を写し、要件ノードだけを数えて `requirementClassCounts` を作る。
3. `MatrixBuilder` は要件行に区分を写し、レポート要約へ機能／非機能件数を載せる。スタンドアロン仕様行は区分未設定とする。
4. `TraceabilityGraphBuilder` は描画ノードへ区分を写す（表示は DSN-0018）。
5. `DecisionsCatalogBuilder.filter` は `requirementClass !== 'all'` のとき、要件項目のみ区分一致で残し、他種別は通過させる。
6. `validate-docs.ts` は `kind === 'requirement'` かつ `requirement_class` が欠落または許容値外ならエラーを返す。

### Trade-offs
- **専用フィールド vs タグ流用**: `tags: [functional]` では必須性も排他性も保証できず、他タグに埋もれる。専用フィールドにすることで検証と UI の第一級扱いが可能になる。
- **解析時デフォルト vs 検証必須**: 解析器が欠落を `functional` に置き換えると誤分類が silently 固定される。解析は未設定のまま通し、検証だけを必須とすることで、ダッシュボードは壊れず文書品質は落とさない。
- **cache 列の追加 vs node_json**: SQLite キャッシュは既に `node_json` にノード全体を持つため、専用列を増やさず再パース（mtime 変化）で伝播する。
