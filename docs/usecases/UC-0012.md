## Content

### Goal
開発者または QA 担当者が、単体から受入までの工程別にテストケース仕様と合否証跡を横断的にレビューし、単体実装カバレッジと契約トレーサビリティを混同せず品質を判断する。

### Trigger
利用者が Web ダッシュボードのテスト仕様・結果タブを開く。

### Preconditions
docs 配下に工程別テストケースが存在し、集約テスト結果レポートが生成されているか、未実行として識別可能であること。

### Main Flow
1. 利用者が工程（単体・内結・外結・システム・受入）を選択する。
2. 当該工程のテストケース一覧と手順・期待結果が表形式で表示される。
3. 集約レポートに証跡がある場合、各 TC の合否と実測が仕様と並んで表示される。
4. 単体工程では、関数・分岐カバレッジの専用ビューで実装網羅を確認する（契約充足度とは別軸）。
5. 形式証跡と補助ハーネスの区別に従い、ブラウザ工程の passed 表示が正当かを確認する。

### Alternative Flows
- カバレッジ未生成: 単体カバレッジは pending として表示され、内結以降のレビューは継続できる。
- 対話実行可能 TC: 詳細から対話型ランナーへ遷移し、パラメータを変えて再確認する。

### Postconditions
工程ごとのテスト不足・証跡の偽装リスク・手動前提 TC が明確になり、追加テストや TC 分割の判断ができる。
