## Content

### Contract
ワークスペースルートに `.traceweave/config.json` を配置し、文書パス・証跡パス・テスト suite 一覧を宣言する。CLI は `process.cwd()` から親へ設定ファイルを探索する。`traceweave test` は各 suite を順次実行し、suite 出力を **traceweave-v1** 形式（`TestResultsReport`、SPEC-0006 の動的結合と同一スキーマ）として読み取り、マージ戦略（既定 `fail-wins`）で単一の集約ファイルへ書き込む。ダッシュボードおよび充足度は集約ファイルのみを結合する。文書トレーサビリティ（`docs/test-cases` の `verifies`）と実行証跡（レポートの TC ID キー）は別レイヤであり、本仕様は**実行証跡の生成・集約**を扱う。

#### 二層モデル（静的 / 動的）
| レイヤ | 正本 | TraceWeave の利用 |
|---|---|---|
| **静的（V字）** | `TC-xxxx.md` の `verifies`, `test_level`, `test_method` | グラフ・マトリクス・充足度の「どの REQ/SPEC に効くか」 |
| **動的（実行）** | 集約 `TestResultsReport` | 各 TC の `execution_status`（passed / failed / pending） |

静的だけでは実行合格にならない。動的だけでは REQ に効かない（TC 文書と `verifies` が必要）。

#### traceweave-v1（集約・fragment 共通）
- ルート: `generatedAt`, `totalTests`, `passedCount`, `failedCount`, `skippedCount`, `results`
- `results` のキーは **TC 文書 ID**（`TC-<STRATUM>-NNNN`、ADR-0009）と一致すること
- 各値: `testCaseId`, `status`（`passed` | `failed` | `skipped` | `pending`）、`durationMs`, `testTitle`, `executedAt`、任意で `errorMessage` / `outputLog`
- 最小例: リポジトリ内 `fixtures/test-reports/traceweave-v1-minimal.json`

#### suite.capture（エンジン判別）
TraceWeave は**テストフレームワークを直接解釈しない**。`capture` は「suite 実行後にどこから traceweave-v1 を得るか」を宣言する。

| 値 | 入力 | TC ID の判別方法 |
|---|---|---|
| `node-test-tap` | Node.js 組み込み `test` + TAP | サブテスト **タイトル文字列**から `TC-(UT\|ITa\|ITb\|ST\|UAT)-\d{4}(-SS)?` を抽出（`SS` 01..99、ADR-0010。推奨: 先頭 `TC-UT-0001:` または `TC-ITb-0001-01:`） |
| `fragment` | `fragment` パスの JSON ファイル | **ファイル内の `results` キー**が TC ID（ランナー非依存・推奨の逃げ道） |
| `aggregate` | 集約パスの JSON | 同上（`run` が集約へ直接書き込んだ場合） |

**フレームワーク別の推奨（capture 実装はプロジェクト側アダプタ）**

| 実行環境 | TC ID をどう載せるか | TraceWeave への渡し方 |
|---|---|---|
| Node `test()` / Vitest `test` / Jest `it` | 第 1 引数タイトルに `TC-xxxx:` | `node-test-tap`、または Vitest JSON 等を **fragment 用スクリプト**で変換 |
| pytest | テスト関数 docstring / `pytest -k` 名 / JUnit `testcase@name` に `TC-xxxx` | JUnit XML → fragment 変換スクリプト |
| `go test` | サブテスト名 `TC-UT-0001` | 標準出力パーサまたは fragment |
| テストフレームワークなし | スクリプトが Oracle 実行後に **JSON を直接書く** | `capture: fragment`（キー = TC ID） |
| 1 コマンド = 1 TC | 引数・環境変数で TC を指定し 1 エントリだけ出力 | fragment または小さなラッパー |

組み込み capture の拡張（`vitest-json`, `junit-xml` 等）は将来の本仕様改訂で追加する。現行実装で組み込み済みは **`node-test-tap` のみ**。それ以外は **`fragment` に traceweave-v1 を書く**（または `run` 内で既存の `traceweave-capture-test-report.mjs` 相当を呼ぶ）。

#### 設定例
- 単一 Node スイート: リポジトリ直下 `.traceweave/config.json`（本製品 dogfood）
- Web + オフラインスクリプト: `.traceweave/examples/config.multi-suite.fragment.json`（参考。`run` は各プロジェクトで実装）

### Inputs
- `.traceweave/config.json`（UTF-8 JSON）
- 任意: `--workspace <dir>`、環境変数 `TRACEWEAVE_WORKSPACE`
- suite ごとの `run`（シェル一行）、任意の `fragment` パス

### Outputs
- 集約 `TestResultsReport`（パスは `testResults.aggregate`、既定 `reports/test-results.json`）
- suite ごとの fragment（任意、既定 `reports/suites/<id>.json`）

### Errors
- ワークスペースを解決できない場合: エラーメッセージを返し終了コード非 0
- suite 実行が非 0 終了の場合: 集約マージ後も CLI 終了コード非 0
- fragment が存在しない、または `results` が欠落: 当該 suite からは読み取り 0 件（警告は将来拡張）

### Constraints
- 集約マージは決定論的であること。
- 同一 TC ID の競合は `merge.onConflict`（`fail-wins` | `last-wins`）に従うこと。
- モノレポ内の複数 subject（表示名）の同時解決は SPEC-0025 の範囲外とする。
- `tags` フロントマターは実行結合に用いないこと（分類・フィルタ用途のみ）。
