# TraceWeave システム概要と境界定義書 (System Overview & Boundary)

本書は、`TraceWeave` システムの存在目的、システム境界（In-Scope / Out-of-Scope）、および開発指示が「システム要求」か「プロセス・構成管理（Chore / Refactoring / Architecture Decision）」かを客観的に判別するための判定基準を定義する正本である。

---

## 1. システムの目的とビジョン (Purpose & Vision)

**TraceWeave** は、現代のソフトウェア開発において要求（NEED）から要件（REQ）、仕様（SPEC）、設計（DSN）、品質方針（QA）、テストケース（TC）に至る V字モデルのトレーサビリティを自動構築・可視化し、工程別（単体・内結・外結・総合・受入）および手法別のテスト地層密度・ピラミッド健全性を自律分析・診断するための品質保証プラットフォームである。

### 解決する課題
1. **要求〜テスト間の追跡断片化**: 文書間やスプレッドシート上で追跡関係が分散し、仕様変更時の影響範囲特定やテスト漏れが発生する。
2. **テスト充足度のブラックボックス化**: 単体テストのコードカバレッジ率（C0/C1）だけでは、「どの業務要件や仕様契約が検証されているか」という仕様観点の品質充足度が証明できない。
3. **テストピラミッドの崩壊**: E2E テストへの過剰偏重（アイスクリームコーン）や中間結合テストの欠落（ひょうたん型）といった不健全なテスト構成の早期検知が困難である。

### コア提供価値
- **双方向トレーサビリティグラフ & マトリクス**: Git 管理された文書群から依存関係ネットワークを有向グラフおよびマトリクス表として自動生成し、影響波及パスを可視化する。
- **工程地層密度 & ピラミッド健全性診断**: 5大工程（Unit / ITa / ITb / ST / UAT）のテスト充足度スコアおよびピラミッドバランスを自動算出し、アンチパターンを警告する。
- **アプリケーションの決め事カタログ**: アクター、ユースケース、要件、仕様、設計、意思決定（ADR）を横断的に閲覧・探索できるカタログビューを提供する。
- **対話型テスト実行 & 実測観測**: 外部パラメータファイルと連携したデータ駆動テスト、および Web 画面上でのパラメータ編集・リアルタイム実行・合否観測を提供する。
- **AI エージェント連携（MCP）**: Model Context Protocol (MCP) を通じて Cursor 等の AI エージェントにトレーサビリティ分析・診断機能を提供する。

## 2. システム境界 (System Boundary)

要求工学に基づき、開発作業や要求分析の対象が「システム内部の要求」か「システム外部のプロセス・管理タスク」かを以下のように明確に分離する。

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ 【システム外部 (Out-of-Scope)】 プロセス・環境・リポジトリ管理の関心事     │
│                                                                             │
│  - Git リポジトリのディレクトリ構成・ファイル配置（クリーンルート規約等）   │
│  - パッケージマネージャ・依存関係管理（package.json, node_modules の配置）  │
│  - ビルド生成物の出力先・ファイル階層配置（dist/ 等）                       │
│  - 実行用ラッパースクリプト（bin/traceweave 等）の作成・配置                │
│  - 文書管理スクリプト（validate-docs.ts 等）や開発プロセス規律              │
│  - CI パイプライン・テストランナーの設定                                    │
│                                                                             │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 【システム内部 (In-Scope)】 実行時ソフトウェアの振る舞い・品質・契約   │  │
│  │                                                                       │  │
│  │  [外部インターフェース層]                                             │  │
│  │   - CLI (Commander.js) によるコマンドライン受付と終了コード           │  │
│  │   - Web Dashboard (HTTP / REST / React UI) による可視化・対話操作     │  │
│  │   - MCP Server (JSON-RPC) による AI エージェント向けツール API        │  │
│  │                                                                       │  │
│  │  [コア処理層]                                                         │  │
│  │   - ドキュメントパーサー & トレーサビリティグラフ構築 (TraceGraph)     │  │
│  │   - ピラミッド充足度・地層密度分析 (BalanceAnalyzer)                  │  │
│  │   - 決め事カタログ集約 & 相互参照解決 (DecisionsCatalog)              │  │
│  │   - テストケース入力解析 & 変更可否判定 (TestCaseInputAnalyzer)       │  │
│  │                                                                       │  │
│  │  [データ永続化・品質保証層]                                           │  │
│  │   - SQLite / JSON ストレージへのレポート出力                          │  │
│  │   - テスト実測値・合否・証跡記録の整合性                              │  │
│  │   - 応答レイテンシ、決定論的解析アルゴリズム                          │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
```

### In-Scope（システム要求の対象）
システムが実行時にアクター（利用者または AI エージェント）に対して提供する**観測可能な振る舞い・入出力契約・データ品質・非機能特性**。
- CLI コマンド（`check`, `matrix`, `report`, `serve`, `build` 等）の引数仕様、出力フォーマット、終了コード
- Web ダッシュボードのグラフ描画、マトリクスフィルタ、詳細インスペクション、トースト通知、対話型テスト実行
- MCP ツール API の入出力スキーマ、エラー表現
- トレーサビリティ解析アルゴリズム（循環参照検知、孤立ノード検出、充足度スコア計算）の正しさ
- データモデル（Node, Edge, StratumMetrics, CatalogEntry 等）の整合性

### Out-of-Scope（システム要求ではないもの）
ソフトウェア実行時の振る舞いではなく、**開発・保守・環境構築・リポジトリ構造の都合**による作業。
- リポジトリルートから個別資材を排除し `src/` や `src/web/` に集約するファイル配置変更（→ `ADR` 起点）
- `package.json` や `node_modules` の移動・カプセル化（→ `ADR` 起点）
- 透過実行用ラッパースクリプト（`bin/traceweave`）の作成や微調整（→ `ADR` 起点または `chore`）
- 開発者ガイド（`DEVELOPER_GUIDE.md`）や規約ルールの整備・更新
- 文書バリデーションスクリプト（`validate-docs.ts`）の調整

## 3. システム要求判定クライテリア (Decision Criteria)

開発指示や改修要望を受けた際、どの文書種別（`NEED` / `REQ` / `ADR` / コミット）で扱うべきかを判定するフローチャートと基準マトリクス。

### 判定フローチャート

```text
[開発指示・要望の発生]
       │
       ▼
【Q1: 実行時ソフトウェアの振る舞い・入出力契約・データ品質の変更か？】
  ├─ No ──► 【Q2: リポジトリ構成・アーキテクチャ方針の決定・変更か？】
  │                ├─ Yes ──► [ADR (docs/decisions/)] または直接作業・コミット
  │                └─ No  ──► [Chore / 開発作業]（文書起票不要、直接実装・コミット）
  │
  └─ Yes ─► 【Q2: 独立した要求ツリーが必要な新規機能・重要仕様か？】
                   ├─ No  ──► [パスD: 直接実装 / 軽量改修]（文書起票不要、直接実装・テスト）
                   │           （自明なバグ修正、内部リファクタ、UI調整、同語反復となる小規模変更）
                   │
                   └─ Yes ──► 【Q3: 抽象的な背景・動機・ユーザー課題から始まるか？】
                                   ├─ Yes ──► [NEED 起点 (パスA)]
                                   │           └─ NEED-xxxx ──► REQ-yyyy ──► SPEC ──► DSN
                                   │
                                   └─ No  ──► [REQ 起点 (パスB)]（具体的機能・主要契約）
                                               └─ REQ-xxxx (depends_on: []) ──► SPEC ──► DSN
```

### 判定マトリクス

| 指示内容・事象の例 | 分類 | 推奨起票先 | 理由 |
|---|---|---|---|
| 「トレーサビリティグラフを有向グラフとして視覚化し、影響パスを追跡したい」 | **システム要求**<br>(ユーザー課題・機能) | `NEED` 起点<br>(`NEED-0007`) | 利用者がダッシュボードを通じて観察する中核機能・視覚表現に関する要望であるため。 |
| 「CLI の check コマンドで循環参照を検知した際にエラー終了コード 1 を返したい」 | **システム要件**<br>(具体的振る舞い) | `REQ` 起点<br>(パスB) | 外部境界での観測可能な終了コード・エラーハンドリング振る舞いであるため。 |
| 「トップレベルの Root に開発資材を置かず、lucid-memories の指針に従ってクリーンに保ちたい」 | **リポジトリ構成管理**<br>(Architecture Decision) | `ADR` 起点<br>(`ADR-0004`, `ADR-0005`) | ソフトウェアの実行時契約ではなく、リポジトリの資産配置・構造整理に関する方針であるため。 |
| 「Web ビルド成果物の出力先を dist-web から dist/web に統一したい」 | **ビルド構成管理**<br>(Refactoring / ADR) | `ADR` 起点<br>(または直接リファクタ) | 内部ビルドパイプラインのパス整理であり、独立したユーザー要求ツリーを組むのは過剰。 |
| 「不要になった一時スクリプトやデッドコードを削除したい」 | **デッドコード整理**<br>(Chore / Cleanup) | 文書起票不要<br>(パスD) | 独立した要求ツリーを作成することが同語反復となる片付け作業であるため。 |
| 「UIのラベル文言やスタイリングを微調整したい」「自明なNull安全チェックを追加したい」 | **軽量改修・直接実装**<br>(Lightweight / Fix) | 文書起票不要<br>(パスD) | 独立した NEED/REQ を新設することが同語反復・過剰儀式となる小規模な改修であるため。直接実装とテストで検証する。 |

## 4. 外部システムインターフェースの管理方針 (External Interface Management)

Cursor / AI エージェント（MCP）、CLI、Web ブラウザ、外部パラメータファイルなど、外部システムとの境界をまたぐインターフェース（外部 IF）については、専用の種別を新設せず、既存のドキュメント階層に以下のようにマッピングして管理する。

```text
[外部アクター]           docs/actors/ACT-xxxx.md
       │                相手システム（Cursor IDE、利用者、外部テストランナー等）の役割・責務
       ▼
[インターフェース契約]   docs/specifications/SPEC-xxxx.md  ★外部IF仕様書（ICD）
       │                通信プロトコル、入出力スキーマ、エラー表現、制約
       ▼
[接続アーキテクチャ]     docs/design/DSN-xxxx.md
                        ポート＆アダプタ構造、リトライ、タイムアウト、フォールバック
```

### 外部 IF 仕様の記述ルール
- **記録先**: `docs/specifications/SPEC-xxxx.md` に集約する。
- **タグによる識別**: フロントマターに `tags: [interface, external, <対象名>]`（例: `[interface, external, cli]`, `[interface, external, mcp]`, `[interface, external, web-api]`）を付与する。
- **仕様の観点**:
  - **提供 IF（Inbound）**: CLI コマンド仕様、MCP Server ツール仕様、Web API 契約など、自システムが提供する完全なスキーマ・契約を記述する。
  - **利用 IF（Outbound）**: ファイルシステム I/O、外部パラメータ JSON など、相手方が提供する IF については、本システムが依存するサブセットおよび異常系ハンドリング契約を記述する。

## 5. 本書の位置づけと今後の拡張 (Traceability & Schema Evolution)

1. **現行の運用**:
   - 本書は `docs/` 直下に配置され、スキーマ検証（`scripts/validate-docs.ts`）のディレクトリ走査をパスしつつ、システム全体の目的と境界を定義する「正本」として機能する。
2. **過剰形式主義の防止**:
   - リポジトリ構成やビルド設定の変更については、無理に `NEED` を起票せず、`ADR`（パスC）として扱う。
   - また、UI文言・スタイリングの微調整、自明なバグ修正、内部リファクタリング、同語反復となる小規模な改修については、文書起票不要の直接実装（パスD）として迅速に反復することを本境界定義書によって保証する。
