## Content

### Context
従来、`docs/test-cases/TC-xxxx.md` のフロントマターに `execution_status` を保持し、本文中に `### Actual Results` および `### Evidence` セクションを設けてテスト実行結果とエビデンスを直接記述する運用が採られていた。しかし、静的仕様文書に動的な実行結果を混在させる方式には以下の深刻な問題が存在した。

1. **静的仕様と動的状態の混同（State Pollution）**: テストを実行するたびに Git ワーキングツリーが変更され、コミットログが汚染される。逆に更新を怠ると、実際の実装が破壊されていても過去の「passed」が恒久的に表示され続ける（空手形）。
2. **LLM による欺瞞的エビデンスの作文（Hallucinated Evidence）**: LLM が「〜を検出し、合格を確認した」といった自然言語の作文を Markdown に書き込むことで、実際のコード実行やオラクル判定を伴わない自己充足的な同語反復（トートロジー）が発生していた。
3. **エビデンスの客観性の欠如**: 本来のテスト証跡は、テストスクリプトの実行プロセス（ランナー）が機械的に出力する終了コード、生ログストリーム、所要時間、アサーション差分といった客観的事実（Raw Fact）であるべきであり、人間の要約や LLM の作文はエビデンスとして無効である。

### Decision
テストケース文書（`docs/test-cases/`）を純粋な「テスト仕様（Test Specification）」として純化し、テスト実行結果およびログエビデンスを完全分離する。

1. **TC ドキュメントの仕様純化**:
   - `docs/test-cases/TC-xxxx.md` の必須見出しを `### Objective`, `### Preconditions`, `### Steps`, `### Expected Results` の 4 セクションに純化する。
   - `### Actual Results` および `### Evidence` の Markdown への記述を廃止・排除する。
   - フロントマターの `execution_status` および `actual_result` の手動記述を廃止し、ドキュメント単体では未実行（pending）を既定値とする。
2. **LLM による意味的作文の禁止**:
   - AI エージェントや開発者がテストケース Markdown 内に実行結果や検証の感想を作文・記録することを厳禁とする。
3. **機械的テストレポート出力の導入**:
   - テストスイート（`npm test` / テストスクリプト）の実行プロセスが、テスト名（`TC-xxxx`）をキーとする構造化テスト結果レポート（`reports/test-results.json` および実行ログ）を機械的・決定論的に出力する。
   - レポートには合否ステータス、実行時間（ms）、タイムスタンプ、標準出力/標準エラー出力、およびエラースタックトレースを記録する。
4. **ダッシュボードおよびパーサーでの動的結合（Join）**:
   - `DocParser` は静的な仕様情報のみを抽出し、レポートが存在する場合に限り、上位層（`buildTraceWeaveReport` 等）で TC ノードと実行結果を動的に結合する。
   - テスト未実行時は「未実施（pending）」と正直に表示し、決して過去の固定値で偽装しない。

### Consequences
- `docs/test-cases/` が静的仕様として安定し、テスト実行による Git コミット差分の汚染が根絶される。
- LLM の作文による虚偽・形骸化エビデンスが完全に排除され、テストの客観性と信頼性が飛躍的に向上する。
- テストスクリプトの実測結果のみが合否判定の唯一の根拠となり、仕様と実装・検証が誠実に対比される健全な品質保証基盤が確立される。
